## Problem Statement

A timed classroom assignment: an interactive Onam quiz web app in HTML + CSS + vanilla
JavaScript, no frameworks and no external JS libraries. 8–10 questions spanning different
areas of Onam, visible progress, a results screen with a score-based message and restart,
and a festive Kerala visual identity. Creativity is graded separately, and bonus challenges
unlock on a timer.

The rubric is not the hard part — every submission in the room will hit it. The separating
question is whether the quiz *mechanic* is Onam-shaped or whether it's a generic quiz with
marigold-coloured buttons.

Deployment target is Zoho Catalyst (user is at Zoho; learning the platform is part of the point).

## What Makes This Cool

**The progress bar and the trophy are the same object.**

A pookalam is a floral floor design built up ring by ring across the ten days of Onam. So:
the quiz opens on bare earth. Every answer blooms one more concentric ring of petals. By
question 10 you have *built* the pookalam, and the results screen is your finished pookalam —
where correct answers bloomed in full colour and wrong ones in muted tones, so **the artwork
itself is your score**, not just a number printed above it.

This does three things at once:
- Satisfies the progress requirement literally (ring count = "Question 4 of 10")
- Gives a reason to reach question 10 that a grey progress bar cannot
- Makes the result screenshot-worthy, which is what "make someone want to complete the whole
  quiz" actually asks for

Rejected during the session: **Onam Sadya plate** (ten dishes on a banana leaf — charming, but
needs ten recognisable hand-drawn food illustrations, and emoji would read as a shortcut) and
**Vallam Kali boat race** (strong motion, but "race" implies a competitor that doesn't exist
single-player).

## Constraints

- **HTML + CSS + vanilla JS only.** No frameworks, no external JS libraries.
- **No Catalyst Web SDK.** `catalystWebSDK.js` from `static.zohocdn.com` is exactly the kind of
  external library the assignment forbids. All backend calls use plain `fetch()`. This costs
  nothing here — no auth is needed — but it is the one line that could actually lose marks.
- **Questions live in a JS data array**, not hardcoded in HTML (explicit rubric item).
- **The pookalam must be inline SVG/CSS you wrote**, not a PNG. A static image satisfies
  "festive" and fails "creativity", because the entire mechanic is that it grows.
- **Timed assignment.** Platform work earns zero rubric points, so it must not be able to sink
  the graded deliverable.
- Data center: **IN** (`active_dc = "in"` in the CLI store) → Slate URLs are `*.onslate.in`.

## Premises

1. "No frameworks or external JS libraries" constrains app code, not hosting. Slate with
   `framework = "static"` serves plain files with no build step and no injected runtime —
   the same category of decision as GitHub Pages. **Agreed.**
2. Corollary: the Catalyst Web SDK is off-limits; backend calls are plain `fetch()`. **Agreed.**
3. The pookalam is inline SVG, not an image. **Agreed** — validated by the wireframe below.
4. The deliverable is a URL, not a folder. A `file://` path doesn't demo and doesn't survive
   being sent to a friend. This is the only reason Catalyst earns its place. **Agreed.**
5. **Catalyst is a schedule risk and the design must neutralise it.** CLI install, login,
   clicking "Start Exploring" on Slate, and a first deploy is realistically 20–40 minutes of
   zero-rubric-point work. The fix is sequencing, not dropping Catalyst: because a static
   Slate app's source directory *is* its output directory, the exact folder that runs from
   `file://index.html` deploys unchanged. Build and verify the graded quiz first; add the
   Catalyst wrapper second. **If the deploy fails, a complete working assignment still ships.**
   **Agreed.**

## Approaches Considered

### Approach A: Slate static only
One folder, no backend, high score in `localStorage`. Full rubric marks, nothing on the bonus
line, and Catalyst does no work a plain file host wouldn't. Effort S, risk Low.

### Approach B: Slate static + leaderboard function + Data Store — **CHOSEN**
A, plus one Advanced I/O function and one Data Store table for a cross-device top-10.
Effort M, risk Med (cross-domain traps). Full rubric + the bonus, and the only option that
exercises Slate, Functions, and Data Store together.

### Approach C: Slate static + shareable result URL
A, plus the finished pookalam encoded in the URL hash so "Share my pookalam" reconstructs your
specific result for whoever opens it. Cleverest product idea, weakest Catalyst answer — hosting
only. Effort S+, risk Low.

## Recommended Approach

**B, staged as A-then-B.** B is the only approach that uses Catalyst as a platform rather than
a CDN, which is the stated goal. Staging it behind a finished A costs nothing and removes all
schedule risk.

**C's share-link is ~20 minutes on top and is not exclusive** — worth adding after B works,
because it degrades to a working feature even when the network doesn't.

### Visual validation

A wireframe was built and rendered to confirm the mechanic reads and that concentric petal
rings are achievable in plain inline SVG (~30 lines of JS, one `<ellipse>` per petal rotated
around the centre).

- Sketch source: `/tmp/gstack-onam-sketch.html`
- Screenshot: `/tmp/gstack-onam-sketch.png`

Three findings from the sketch, all folded into the spec below:

1. **One ring per question, not five rings for ten questions.** With 5 rings, half of all
   answers produce no visible change — which kills the mechanic outright. 10 thinner, denser
   rings means every single answer blooms something. *This is the most important correction.*
2. **The empty state must read as "waiting", not "broken".** Dashed grey outlines look like a
   loading skeleton. Use warm bare earth, a faint guide circle, and a centre seed.
3. **Under ~600px the pookalam pushes the question below the fold.** It must shrink to a
   compact ring-meter on mobile.

### Two SVG/CSS precedence traps hit during the build

Both made the pookalam render as nothing at all, and both are worth recording because
neither throws an error:

1. **A stylesheet `fill` beats a presentation attribute.** `.petal { fill: none }` in CSS
   silently overrode every `setAttribute('fill', colour)` from JS, so all 359 petals stayed
   transparent. Fix: declare no `fill` in CSS and set it via inline `style.fill`, which wins.
2. **A CSS `transform` replaces the SVG `transform` attribute entirely.** The bloom keyframe's
   `scale()` wiped the `rotate(...) translate(...)` that positions each petal, collapsing the
   whole ring to the centre. Fix: positioning goes on a wrapper `<g>` as an attribute, the
   scale animation goes on the inner `<path>` via CSS. Different elements, no conflict.

A third issue was a design flaw, not a bug: muting each ring to a desaturated twin of its own
hue meant the **white jasmine ring's "wrong" state was invisible** against cream. Replaced with
one shared grey-taupe (`#CBC3B4`) for every wrong answer, so missed questions are countable at
a glance regardless of ring position.

`.catalyst/slate-config.toml`:
```toml
framework = "static"
deployment_name = "default"
```

No `_redirects` needed: that file exists to catch the Catalyst SDK's legacy `/app/` redirect,
and we are deliberately not loading the SDK. No `client-package.json` either — optional for
Slate and SDK-only in effect.

**Do NOT use a `client/` directory.** Web Client Hosting is legacy; Slate is the current service
and the two behave differently for routing and function URLs.

### Question set (10, deliberately spread)

Data shape is exactly as the assignment specified:

```javascript

  { question: "...", options: ["...","...","...","..."], answer: "..." }

```

One question each from: pookalam flowers (thumba), the Mahabali legend, Onam sadya, Vallam Kali

### Pookalam spec

- **10 rings, ring index `i` = 0..9, one per question.**
- Ring radius: `14 + i * 10` (outer ring ≈ 104 in a 240 viewBox).
- Petals per ring: `8 + i * 2` (8 → 26). Density is what makes it read as a pookalam rather
  than a marigold burst.
- Petal shape: SVG `<path>` teardrop, not `<ellipse>` — the sketch's ellipses read as a
  sunburst. One petal per `<path>`, `transform="rotate(a cx cy)"`.
- Palette cycles marigold `#F08C00`, white `#FFFDF7`, magenta `#9B1B5A`, forest `#1E5B3A`,
  turmeric `#F5C518`, temple red `#A8201A`.
- **Correct answer** → ring in full saturation. **Wrong answer** → same ring desaturated/muted.
  The pookalam always completes; its colour *is* the score.
- Bloom: stagger petals via `animation-delay: calc(var(--i) * 18ms)`, `scale(0)` → `scale(1)`
  with `cubic-bezier(.34, 1.56, .64, 1)` for the pop. ~380ms per ring.
- Paint order: outermost ring first so inner rings layer on top.
- `@media (prefers-reduced-motion: reduce)` → opacity fade only, no transform.

### State machine (js/app.js)

Four states, one `render()`, no router:

`start` → `question` → `feedback` → (`question` | `result`) → `start`

State object: `{ screen, index, score, results[] }`. `results[]` holds per-question
correctness, which is what drives ring colour and what the share-link would encode.

### Live event mode (host session + QR join)

Superseded the single-player-only backend. The host opens a round, the room scans a static QR,
and the dashboard polls a leaderboard that climbs as people answer. **The graded solo quiz at
`/` is untouched** — live mode is additive via hash routes, so rubric marks never depend on it.

| Route | Purpose |
|---|---|
| `#` (no hash) | the graded single-player quiz |
| `#host` | dashboard: giant QR, session code, live leaderboard, Start / Close |
| `#join` | participant flow for a scanned phone |

**Hash routes, not paths.** A hash needs zero server configuration, so it cannot 404 on static
Slate hosting. That matters when the join URL is encoded in a QR projected in front of a room.

**The QR is a static committed SVG**, generated at dev time with `npx qrcode` — only the image
ships, so the app still has zero external JavaScript libraries. It points at a fixed `/#join`
and the *session code is shown separately in large type*. That separation is what lets one
static QR serve every round: `#join` asks the function which session is currently open.

**Session codes** draw from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — no `O`/`0` or `I`/`1`, because
the code gets read off a projector and typed by hand when a phone camera won't focus.

#### Why not lockstep Kahoot-style

Catalyst allows **10 concurrent executions per function per environment** and returns HTTP 429
beyond that. Lockstep means every phone polls for the current question index continuously and
every answer lands in the same instant — 30 devices is straight through the ceiling. Self-paced
play spreads writes naturally: the dashboard polls at 3s, each player writes once per answer.
This is a robustness decision, not a laziness one.

### Data Store schema — two tables

**`Pookalam_Scores`** (players; also holds solo scores under `session_code = 'SOLO'`)

| Column | Type | Notes |
|---|---|---|
| `session_code` | `varchar(8)` | `'SOLO'` for single-player runs |
| `player_name` | `varchar(40)` | varchar hard-caps at 255 and silently clamps above it |
| `score` | `int` | correct answers so far |
| `answered` | `int` | questions answered so far — drives the "7/10" progress on the board |
| `total` | `int` | so a future 15-question version stays comparable |

**`Quiz_Sessions`** (rounds)

| Column | Type | Notes |
|---|---|---|
| `session_code` | `varchar(8)` | the 4-char code shown on stage |
| `session_status` | `varchar(10)` | `'open'` or `'closed'` |

**Closing a round reaches every phone live.** When the host closes a session, players still
mid-quiz poll `GET /session/status?code=XXXX` (3s, the same cadence as the dashboard) and, on any
non-`open` status, stop answering and show a "the round has ended" screen with their final score.
Scoped to the player's own code — not `currentSession()` — so opening a fresh round elsewhere
still reads as closed for the old one instead of silently attaching the player to a stranger's.

> **Named `session_status`, not `status`.** Catalyst rejects reserved column names — it refuses
> `priority` with `INVALID_OPERATION: Column name cannot contain reserved keywords`. `status`
> was not worth the risk of finding out mid-demo.

**Session codes are globally unique, not just unique-among-open.** `/session/open` regenerates
the code until it is unused across *all* history (closed rows live forever). This is a correctness
invariant, not cosmetics: `board()` scopes players by `session_code` alone, so a reused code would
merge a past round's players into a live leaderboard. The leaderboard itself orders by
`score DESC, answered DESC, ROWID ASC` — deterministic so equal scores don't flicker between polls,
and finishing more questions breaks the tie.

`ROWID`, `CREATEDTIME`, `CREATORID`, `MODIFIEDTIME` are automatic — **never create them**.

#### ZCQL injection is a real surface here

ZCQL has **no parameter binding**, so every query is built by string concatenation. Session
codes are therefore *whitelisted* to `/^[A-Z0-9]{1,8}$/` and rejected outright on failure, not
escaped. Verified live: `GET /board?code=A' OR '1'='1` returns `{"error":"bad code"}` without
touching the database. Player names never enter a query — they go through `insertRow()`, which
the SDK parameterises.

**Function `quiz_api` — Advanced I/O, `node24`**

Advanced I/O, not Basic I/O: Basic I/O returns a bare string with no status codes or headers
and `write()` can only be called once, so it cannot carry JSON properly.

Single endpoint, method-switched — no path routing needed:
- `GET  …/server/quiz_api/execute` → top 10
- `POST …/server/quiz_api/execute` body `{name, score, total}` → insert, then return top 10

```javascript
const catalystApp = catalyst.initialize(req, { scope: 'admin' });
```
Admin scope because App User INSERT permission is **off by default** — without it, writes
return "No privileges to perform this action".

Top-10 query:
```sql
SELECT player_name, score, total FROM Pookalam_Scores ORDER BY score DESC LIMIT 0, 10
```
- Unwrap the result: `result.map(r => r.Pookalam_Scores).filter(Boolean)` — raw ZCQL results are
  wrapped under the table-name key. Skipping this is the single most common Data Store bug.
- **No `AS` aliases** — ZCQL silently drops them and returns the original column name.
- Table and column names are case-sensitive and must match the console exactly.

Server-side validation before insert (the endpoint is public — see Open Questions):
- `total === 10`, `Number.isInteger(score)`, `0 <= score <= total`
- `name` trimmed, length clamped to 40, empty → `"Anonymous"`
- **Strip emoji before insert** — Data Store silently stores 4-byte UTF-8 as `?`, so
  "Sibhi 🌼" lands as "Sibhi ?": `name.replace(/[\u{10000}-\u{10FFFF}]/gu, '')`

### The three cross-domain traps (pre-empted)

These are where Catalyst projects actually break. All three are cheap to avoid and expensive
to debug cold.

1. **Function URLs must be absolute.** Slate serves from `*.onslate.in`; functions live on
   `*.catalystserverless.com`. A relative `/server/quiz_api/execute` does not error — it hits
   Slate's own fallback and returns HTML with status 200, so `fetch` "succeeds" and
   `JSON.parse` explodes somewhere unrelated.
2. **Append `/execute`.** The URL printed by `catalyst deploy` omits it and 404s as shown.
3. **Pick exactly one CORS mechanism.** Add the bare Slate domain under
   Console → Authentication → Authorized Domains (CORS enabled) and set **no** CORS headers in
   function code. Doing both yields a duplicated `Access-Control-Allow-Origin`, which every
   browser rejects — with a CORS error that looks like the origin is wrong when it isn't.
   Only set CORS headers for `localhost`.

Frontend base URL — real values, verified 2026-08-19:

```javascript
const LOCAL = ['localhost', '127.0.0.1'].includes(location.hostname);
const API = LOCAL
  ? 'http://localhost:3000/server/quiz_api/execute'
  : 'https://onam-utsavam-60083782173.development.catalystserverless.com/server/quiz_api/execute';
```

**Project identity (created via CLI, linked in `.catalystrc`):**

| Field | Value |
|---|---|
| Project name | `onam-utsavam` |
| Project ID | `53069000000013054` |
| Org / env ID | `60083782173` (env `Development`, type 3) |
| Dev domain | `onam-utsavam-60083782173.development` |

The `Asia/Kolkata` timezone is why `CREATEDTIME` needs the +330 offset correction if the
leaderboard ever displays timestamps — Catalyst stores it in project-local time with no UTC
marker, so `new Date(row.CREATEDTIME)` is silently 5.5 hours wrong.
Port 3000 is the stable function port under `catalyst serve`. Never point at the Vite port.

**The leaderboard must fail soft.** Wrap every call in `try/catch` with a ~4s
`AbortController` timeout. On any failure, hide the leaderboard block entirely and still show
the score and the finished pookalam. The graded experience must never depend on the network.

## Success Criteria

- 10 questions from 10 different areas of Onam, stored in a JS array.
- Every answer visibly blooms exactly one ring. No answer is a visual no-op.
- Progress readable two ways at all times: "Question N of 10" + percentage, and ring count.
- Results screen: score, total, score-based message, finished pookalam, Play Again.
- Full flow works from `file://index.html` with no server and no network.
- Same folder deploys to Slate unchanged and works at the `*.onslate.in` URL.
- Leaderboard shows a cross-device top 10 — and its failure is invisible to the player.
- Legible and usable at 360px wide.
- Zero external JS libraries. Verifiable: no `<script src="http...">` anywhere.
